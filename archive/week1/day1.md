## 二、核心知识（复习版）

### 1. 一次请求的完整链路

```
messages 数组（system + user）
   ↓ ① HTTP POST /chat/completions，stream: true
服务端 tokenize → Transformer 逐 token 采样
   ↓ ② 每生成一个 token 推一帧：data: {"choices":[{"delta":{"content":"你"}}]}
客户端逐行读 → 解析 JSON → 打印 delta.content
   ↓ ③ 最后一帧 [DONE]，附带 usage 与 finish_reason
计算 token 与成本
```

### 2. 四个关键字段

| 字段 | 作用 | 要点 |
|---|---|---|
| `model` | 用哪个模型 | 能力、价格、速度差异巨大 |
| `messages` | 对话历史 | 数组；role 有 system / user / assistant |
| `stream` | 是否流式 | true = 边生成边推；false = 一次性返回 |
| `temperature` | 采样随机性 | 0 稳定、>1 发散；**思考模式下失效** |

### 3. SSE 协议（流式的本质）

服务端不返回完整 JSON，而是持续下推文本行：

```
data: {"choices":[{"delta":{"content":"你"}}]}

data: {"choices":[{"delta":{"content":"好"}}]}

data: [DONE]
```

客户端逐行读、取 `delta.content`、立刻打印 → 看起来像打字机。
**没有魔法，只是一行行文本。**

### 4. Token 与计费

- token 是模型处理与计费的最小单位；中文约 1 字 ≈ 0.6–1 token
- **输入 token = system 消息 + user 消息 + 对话模板特殊标记**（带 tools 还要加工具定义）
- 输入、输出分开计价，输出通常贵 4 倍左右
- **每次请求都要重新发全部上下文**——模型服务端不保存你的历史
- 缓存命中价格极低（约为未命中的 1/50），所以固定写法的长 system prompt 有优化空间

### 5. TTFT 与总耗时

| 指标 | 含义 | 影响 |
|---|---|---|
| TTFT（首字延迟） | 从发请求到第一个字出现 | 用户"感觉快不快" |
| 总耗时 | 全部生成完 | 用户"等多久" |

产品优化优先看 TTFT。

### 6. Temperature 的本质

```
概率 = softmax(logits / T)
```

| 温度 T | 最高分 token 的概率 | 效果 |
|---|---|---|
| 0.1 | ≈ 0.9999 | 几乎必然选它，稳定 |
| 1.0 | ≈ 0.665 | 有随机性 |
| 2.0 | ≈ 0.506 | 接近抛硬币，容易跑题 |

**任务 → 温度对照：**

| 任务 | 温度 |
|---|---|
| 字段抽取 / 分类 / JSON 输出 | 0 |
| 客服问答 / RAG 回答 | 0–0.3 |
| 通用对话 / 写作 | 0.7 |
| 起名 / 文案 / 头脑风暴 | 0.9–1.2 |

> 注意：`temperature=0` 不是数学上的绝对确定（浮点、批处理会带来微小差异）。

### 7. finish_reason 的四种取值

| 值 | 含义 | 处理方式 |
|---|---|---|
| `stop` | 自然说完 | 正常 |
| `length` | 撞到 max_tokens 被截断 | 提高预算或分片续写 |
| `content_filter` | 被安全策略拦截 | 换问法 / 提示用户 |
| `tool_calls` | 模型要求调工具 | 进入 Agent 循环 |

> `max_tokens` 是刹车，不是目标。

## 五、答案与批改

### Q1 输入 token 由什么组成 —— ⚠️ 半对

你的答案复述了 token 的定义，但没回答"组成"。正确答法：

```
输入 token = system 消息 + user 消息 + 对话模板特殊标记（+ tools 定义）
```

两个推论：
- 模型无记忆，每轮都要重发全部历史 → 重复付费
- 人设越长，每次请求越贵

验证方式：对比长短 system 两次运行的输入 token 数。

### Q2 输出 token 为什么不同 —— ❌ 未答

1. **采样随机**：按概率抽签，抽到的词不同
2. **停止位置不同**：EOS 出现在哪一句不确定
3. **token ≠ 字**：换种说法，切分结果就不同

结论：输出 token 是结果，不是参数，只能通过提示词和 max_tokens 约束。

### Q3 中断后已输出内容还能用吗 —— ✅ 答对

能。流式是边生成边推，已推过来的内容保存在你这边。
补充：**不能"续传"**，要接着写只能把已有内容当上文重新请求。

### Q4 10 人同时用会先出什么问题 —— ❌ 未答

按发生顺序：

| 顺序 | 问题 | 表现 | 解法 |
|---|---|---|---|
| 1 | 串行阻塞 | 第 10 人等 10 倍时间 | 异步 / 并发 |
| 2 | 速率限制 | 大面积 429 | 限流 + 指数退避 |
| 3 | 会话状态无处存 | 重启丢失、多人串台 | 按用户 ID 存数据库 |
| 4 | 成本失控 | 有人刷爆额度 | 用户配额 + max_tokens 上限 |
| 5 | key 泄露 | key 硬编码在客户端 | key 只放服务端 |

**第 1 条最致命**：同步脚本一个人问 5 秒，十个人就是 50 秒。

### Q5 为什么越聊越贵 —— ✅ 答对

上下文线性增长，每轮重新发全部历史。第 20 轮的输入 token 可能是第 1 轮的 20 倍。
